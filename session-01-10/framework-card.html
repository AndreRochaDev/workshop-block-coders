The loop you run, every task

  • 1 · Explore
  • 2 · Plan
  • 3 · Execute
  • 4 · Verify
  • 5 · Commit
  • Explore (Ask): what exists already? Don't build what's there.
  • Plan (Plan agent): files to change, one test per rule, what's out of scope. Make it ask questions before it writes anything.
  • Execute (Agent): from the approved plan, in one task-sized chat.
  • Verify: tests green, and you read the diff. Tests passing is not the same as correct.
  • Commit: small, message drafted from the diff, signed off by you.

Keep the context clean

  • One task, one chat. New chat for the next task.
  • Everything is re-sent every turn: quality drops as the window fills.
  • Point at what matters with #file; don't dump the repo in.
  • Watch the token usage indicator; /compact when a session must continue.
  • Step back, don't patch forward. Restore the checkpoint and re-prompt precisely.
  • Checkpoints don't undo terminal commands, migrations or anything external. Git does.

Teach it your project

  • .github/copilot-instructions.md joins every chat in the repo. /init drafts it; then cut it down.
  • Imperative voice, Do/Don't pairs, one rule per mistake it actually made.
  • Record decisions you've made (architecture, conventions) so it stops re-deciding.
  • Formatting belongs to linters and .editorconfig, not to the instructions file.
  • An outdated instructions file is worse than none.

Review checklist for generated code

  • Does it do only what was asked? Delete the rest.
  • Did the domain model change? (init → set, nullability, defaults)
  • Migrations: what happens to existing rows?
  • Concurrency: two requests at the same moment.
  • Authorization: who is allowed to do this?
  • Errors: do they leak anything?
  • Tests: do they assert behaviour, or just run the code?
  • Docs it wrote: true against the code, or plausible fiction?

Trust vs challenge

Trust, then verify

  • Changes proven by tests you have read
  • Boilerplate that follows an existing pattern
  • Explanations you can check against the code

Always challenge

  • Domain model changes and migrations
  • Concurrency, authorization, anything security-shaped
  • Anything outside the plan you approved

Seven habits

  1. Small tasks, one chat each
  2. Plan before code
  3. Say what's out of scope
  4. Step back, don't patch forward
  5. Grow the instructions file from real mistakes
  6. Commit after every green run; never run an agent on a dirty tree
  7. Review with fresh eyes: a new chat, and your own
Never paste secrets or customer data into a prompt. You own every line you merge — an instructions file is guidance, not a security control.
